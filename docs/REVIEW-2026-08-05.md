# Scour adversarial review

Reviewed commit: `e86ba6167a25f8227d45205599430710fec291b4`  
Review host: Linux 6.18.40, x86-64, Rust/Cargo 1.97.1  
Date: 2026-08-05

## Verdict

Scour is already a serious search engine, but it is not yet a trustworthy mirror of the filesystem. The query engine is unusually well measured and defended; the weak boundary is exactly the one the author suspects: turning a changing, partially failing namespace into durable rows.

The most expensive defects are not obscure portability details:

1. Linux inotify overflow is reported by `notify` in a shape Scour silently drops. A sufficiently large `git clone`, build, or `rm -rf` can therefore produce permanent drift with no status indication.
2. A failed index write discards the staged rows; the engine ignores the error, announces a revision, clears `pending`, and does not retry. I reproduced a failed commit followed by a successful retry and zero indexed rows.
3. An ordinary non-cold restart does not reconcile anything by default. There is no journal, yet `scan.on_start` defaults to false. Offline changes and any crash-window loss therefore survive indefinitely.
4. The startup scan is queued before watching begins. The otherwise-correct “watch first, walk second, replay queued events” rule is absent on the most important scan of all.
5. Distinct non-UTF-8 Unix names collapse through `to_string_lossy`, receive the same path identity, and become one row. This is a direct path-identity correctness failure, not a display blemish.
6. Reconciliation is scoped by text path but not `SourceId`. Overlapping sources can sweep or remove one another, while source IDs themselves are transient configuration-array positions that are persisted without a source map.
7. The path-identity change fixed replacement-by-rename, but broke the explicit hard-link disk-usage contract and leaves metadata stale through aliases.
8. Mount failure is inferred from “the root is empty.” That protects an absent removable volume by making a genuinely emptied source impossible to reconcile, and it does not protect against an unmount or I/O failure after the one pre-scan check.

I would not spend the next engineering cycle on `io_uring`, a reduced `statx` mask, or ext4 inode ordering. The repository's measurements and my runs agree that the warm walk is not the critical path. I would first make overflow, reconciliation, I/O failure, path representation, and source qualification correct; then attack the index builder and integrated watch+enumeration path. For cold NTFS and the intended non-Linux targets, bulk metadata APIs remain worthwhile.

## Findings, ordered by user cost

### 1. [BUG — critical] The Linux overflow event is silently discarded

**One sentence:** when inotify says “events were lost,” Scour emits no rescan, so overload converts a bounded delay into permanent invisible files or permanent ghosts.

**Evidence.** Scour's `translate` handles `EventKind::Any | EventKind::Other` by iterating `event.paths` and emits nothing when that list is empty (`crates/scour-source-fs/src/watch.rs:312-320`). The error callback has a correct empty-path fallback, but overflow is not delivered through that callback. In the exact installed dependency, `notify-8.2.0/src/inotify.rs:212-214`, `IN_Q_OVERFLOW` becomes:

```rust
Event::new(EventKind::Other).set_flag(Flag::Rescan)
```

and is sent before any path is attached. The repository's own 65,536-item changes channel blocks the watcher callback when full (`crates/scour-engine/src/engine.rs:204-207,483-492`). Linux's inotify queue is finite; while the worker synchronously scans or commits and the callback blocks, the kernel continues receiving filesystem changes. A million-file deletion is precisely the workload that reaches this path.

The same conceptual mistake is ignoring `Event::need_rescan()`: the backend deliberately exposes a rescan flag rather than promising a particular `EventKind`/path shape.

**Certainty:** certain. A deterministic unit reproduction needs no kernel tuning: construct `Event::new(EventKind::Other).set_flag(Flag::Rescan)` with no paths, pass it through the translation adapter, and assert one global `Change::Rescan { path: "" }`. A real integration proof should stall the worker, generate more than `max_queued_events`, quiesce, and compare the index to a raw walk.

**Action and cost.** Check `event.need_rescan()` before normal translation. Emit the supplied subtree paths, or the empty global rescan when there are none, and return. Add the synthetic unit test and one overload integration test. This part is hours, not weeks. The larger fix is to expose overflow counters and last successful reconciliation in status so recovery is observable.

### 2. [BUG — critical] An I/O error loses changes and is reported internally as success

**One sentence:** transient `ENOSPC`, `EIO`, or permission failure can permanently remove staged changes while the engine clears its dirty state and wakes clients as though the commit succeeded.

**Evidence.** `NativeIndex::flush_prepare` takes and clears `inner.staged` before durable writes (`crates/scour-index-native/src/index.rs:299-309,408-443`). `Index::commit` then writes alive bitmaps, builds the segment, writes it, and finally saves the manifest (`index.rs:1057-1089`). Any `?` after `take_staged` drops the only `Vec<Entry>` holding those rows.

The scratch fault injection staged `/should-survive`, made the index directory unwritable for one commit, restored it, and retried:

```text
first=Err(PermissionDenied { path: ".../native-index.tmp" })
retry=Ok(())
entries_after_retry=0
```

The engine makes this worse:

- scan batches discard `index.apply` errors (`crates/scour-engine/src/engine.rs:918-925`);
- watcher batches inspect only the `Ok` case and otherwise continue dirty (`engine.rs:571-589`);
- commit ignores the result, calls `touched`, sets `pending=0`, and clears `dirty` (`engine.rs:673-681`);
- sweep uses `unwrap_or(0)` (`engine.rs:851-854`);
- `begin_generation` failure returns “success/no retry” (`engine.rs:808-813`);
- maintenance and shutdown commits are similarly ignored (`engine.rs:538-542,731,757,764`).

During a full reconciliation this can be destructive in both directions. If one apply batch fails but the scan report remains “trustworthy,” sweep deletes older unstamped rows. If the final commit fails, the new rows vanish while the revision tells the GUI to refresh.

**Certainty:** certain; reproduced at the public `Index` API. `EACCES` was merely the deterministic injection. The same ownership transition is used for every write error.

**Action and cost.** Make `Pending` recoverable: do not mutate searchable/durable state or clear staging until the full transaction can be published, or restore the staged/overlay state on every error. An append-only small WAL is another defensible design. In the engine, retain `dirty`/`pending`, do not advance revision, record a typed health code, retry with bounded backoff, and stop reconciliation before sweep if any batch failed. Add failpoints at manifest temp create/write/fsync/rename, every segment part, alive replacement, directory fsync, and sweep. This is a medium-to-large correctness change (several days plus fault tests), but it is release-blocking work.

### 3. [BUG — critical] Existing index damage or read failure fails open as an empty, valid index

**One sentence:** a recoverable manifest permission error or a truncated alive bitmap is interpreted as “there are no entries,” after which normal housekeeping can erase evidence and rebuild from an incomplete premise.

**Evidence.** `open_or_create` maps every `read_to_string` error—not only `NotFound`—to `Meta::default()` (`crates/scour-index-native/src/index.rs:181-208`). The scratch reproduction chmodded a valid manifest to mode 000:

```text
MANIFEST_READ before=1
MANIFEST_READ mode=000 reopen=Ok(0)
```

With default metadata, `sweep_orphans` treats all real segment files as unreferenced. A transient inability to read one small JSON file can therefore destroy an otherwise intact index.

Separately, `Live::open` reads `.alive` but never validates `len == rows.div_ceil(8)` or spare bits (`crates/scour-index-native/src/segment.rs:81-113`). An empty alive file reopens successfully with zero entries:

```text
TRUNCATED_ALIVE reopen=Ok(0)
```

The immutable parts perform structural parsing, which catches many truncations, but there are no checksums. Plausible bit flips can silently change names, numeric columns, postings, source IDs, or liveness.

**Certainty:** certain for both reproductions; high for plausible undetected bit corruption.

**Action and cost.** Treat only `ErrorKind::NotFound` as a new index; propagate every other manifest I/O error. Validate alive length, tail bits, and row counts across every segment component. Put a row count and checksum in each component/header, including the atomically replaced alive file. Open should fail closed as `IndexCorrupt` and the wiring layer may then choose a full rebuild. The manifest fix is minutes; comprehensive integrity metadata is a small format revision and several days of corruption tests.

### 4. [BUG/RISK — critical] Restarts have no catch-up, and startup opens a scan/watch race

**One sentence:** changes made while the daemon is down, plus changes in the startup scan-to-watch interval, can remain wrong forever under the default configuration.

**Evidence.** `ScanCfg::default().on_start` is false (`crates/scour-config/src/schema.rs:142-150`). `scourd` queues a rescan only when that flag is true or the index is cold (`apps/scourd/src/main.rs:64-69`). `FsSource` advertises no `Caps::JOURNAL`; `notify` starts from “now.” Therefore a create, delete, rename, or metadata change while the service is stopped has no path into the index on an ordinary restart.

Even when a cold/on-start scan is queued, it is queued before the socket is bound and before the watch thread starts (`apps/scourd/src/main.rs:64-98`). The worker can start scanning immediately. The comments record 15.1 s to install 342,000 watches. A path observed by the scan and then changed before its directory receives a watch is covered by neither mechanism.

The engine already has the correct rule for a watcher-requested subtree: cover first, scan second, and process queued watcher changes after the synchronous scan (`crates/scour-engine/src/engine.rs:590-635`). Startup bypasses that rule. This queue ordering is genuinely good once coverage exists: watcher events accumulate while the worker scans and are replayed after sweep, so later events win. The defect is failure to establish the barrier at startup.

Crash durability magnifies the issue. A kill during the alive-before-new-manifest interval is allowed to lose the last replacement commit; with no next-start reconciliation, that derived-data loss becomes permanent.

**Certainty:** certain for offline changes and the ordering; high for a missed startup mutation. A deterministic test needs a controllable source/watch barrier: pause scan after a directory, mutate it before `start_watching` covers it, finish, and compare.

**Action and cost.** Until durable journals exist, default to a background reconciliation on every start for every watched filesystem source. Serve the old index immediately if startup latency matters, but mark it “catching up.” More importantly, establish coverage before the baseline: on Linux add a watch to each directory before enumerating it, buffer events, finish/stamp/sweep, then replay. This can be one integrated traversal rather than `notify` performing a second 15-second walk. Persist a clean-shutdown/config/source fingerprint; a source without a valid journal cursor always rescans. Moderate work on Linux, larger cross-platform work, and worth it.

### 5. [BUG — critical for affected trees] Lossy path conversion merges real files

**One sentence:** Scour cannot represent the Unix namespace it claims to index because invalid UTF-8 is replaced before identity, storage, stat, exclusion, and watch processing.

**Evidence.** `path::from_path` uses `Path::to_string_lossy()` (`crates/scour-source-fs/src/path.rs:24-26`); scan also lossily converts the name (`scan.rs:245-246`); every filesystem row is then identified by `EntryId::path_hash(source, path)` (`scan.rs:361-374`). The index's exact collision confirmation is sound only when the stored string is an injective representation of the OS name.

I created byte names `same-\xfe` and `same-\xff`. Both became `same-�`, both received the same `EntryId`, and staged-path replacement kept only one. The scan reported the root plus two files (3 entries); the committed index held the root plus one file (2 entries). `stat` cannot round-trip either original because converting the replacement character back produces a different byte sequence.

Windows has the analogous problem for ill-formed WTF-16 `OsString`s. Newline, tab, escape, and other control bytes are valid UTF-8 and survive, which creates a separate rendering problem below.

The existing non-UTF-8 test exercises an arena decoder and “does not panic”; it never creates two distinct OS names that collide or checks round-trip stat/removal.

**Certainty:** certain and reproduced.

**Action and cost.** Preserve a platform-native canonical path key: raw bytes on Unix and WTF-16 code units on Windows. Keep a separate escaped/display string for query and wire use, or define a reversible byte encoding with an unambiguous tag. Identity and exact confirmation must use the native key. This changes `scour-core` vocabulary, the wire representation, and on-disk format, and thus requires the same-commit contract update. It is expensive (likely one to two weeks across all frontends), but every partial fix leaves collisions. Add byte-level tests for invalid UTF-8, literal replacement characters, newlines, embedded escape bytes, and round-trip stat/remove.

### 6. [BUG — high] Reconciliation is not source-qualified, while source IDs are not actually stable

**One sentence:** source A can delete source B's rows when roots overlap, and config removal/reordering can strand or misattribute persisted rows even when roots do not overlap.

**Evidence.** The core trait is `sweep(under: &str, generation: u64)` with no `SourceId` (`crates/scour-core/src/traits/index.rs:33-46`). `Change::RemoveSubtree` and `Change::Rescan` also carry only a path (`crates/scour-core/src/types/change.rs:27-38`). Native sweep visits every segment and matches only the directory/name path. The engine selects the first source whose root textually owns a path (`crates/scour-engine/src/engine.rs:768-779`), not the longest or the source that emitted an event.

The scratch index held `(source 0, /shared/file.txt)` and `(source 1, /shared/file.txt)`. Rescanning source 0 and sweeping `/shared` removed source 1's row:

```text
OVERLAP before=2 swept_by_source0_rescan=1 after=1 sources_left=[0]
```

The test claiming a later scan retains source precision uses disjoint `/home/u` and `/mnt/depo` roots (`crates/scour-index-native/tests/whole.rs:825-885`); path scoping, not source scoping, makes it pass.

At wiring time, `SourceId` is just `.enumerate()` over the config array (`apps/scourd/src/wire.rs:25-35`). The manifest persists no source UUID/name/root mapping (`crates/scour-index-native/src/index.rs:93-115`). Removing a source never purges it. Reordering sources rebinds old numeric IDs to new meanings. Adding a source with a warm index and default `on_start=false` never populates it. This contradicts the `SourceId` comment that configuration order is stable for the lifetime of an index (`crates/scour-core/src/types/entry.rs:10-14`).

**Certainty:** overlap is certain and reproduced; config reorder/removal follows directly from persisted format and startup policy.

**Action and cost.** Carry `SourceId` on reconciliation and removal all the way through `Change`, `Index::sweep`, hidden-prefix overlays, and native matching. Persist a stable source UUID plus normalized root/config fingerprint in the manifest; on config change migrate, purge removed sources, and reconcile changed/new roots. Select longest-root ownership for path-initiated operations. As an immediate safe guard, reject overlapping roots across sources at startup. Full support is a medium format/trait change; rejection is a day.

### 7. [BUG/RISK — high] “Empty” and “unmounted” are conflated, and mount identity is never validated

**One sentence:** the protection against an absent mount makes a legitimately emptied source permanently stale, yet a mid-scan unmount or partial I/O failure can still authorize a destructive sweep.

**Evidence.** Before walking, scan marks a whole source `root_unreadable` when any root is unreadable **or empty** (`crates/scour-source-fs/src/scan.rs:146-172`). The engine refuses sweep in that case. In the scratch reproduction a source containing `old.txt` was scanned, the file was deleted, and an explicit second rescan still reported two index entries. A truly empty root is also retried forever on the absent-volume backoff.

For a multi-root source, `roots.iter().any(...)` means one empty/removable root disables reconciliation for every healthy root, although all are still scanned and upserted.

The check is a one-time `read_dir` before the parallel walk. If a mount disappears, a network share returns `ESTALE`, or permissions change after that check, walker errors merely increment `report.unreadable`; `trustworthy` ignores that count and sweeps (`crates/scour-engine/src/engine.rs:831-861`). Partial inability can therefore remove rows that were merely unreachable. Conversely, metadata errors are reduced to `None`, and an entry is upserted with `Meta::UNKNOWN` (`scan.rs:260-278`), so a file that vanished between readdir and stat can be stamped into the new generation as a ghost.

**Certainty:** empty-source behavior is certain and reproduced. Mid-scan destructive sweep is high-confidence; a mount-namespace phase test would settle exact backend error shapes.

**Action and cost.** Persist and compare the expected mount/device/filesystem identity per root. An existing mounted root that is empty is authoritative and must sweep. A root expected to be a mount but currently backed by its parent filesystem is unavailable. Record identity before and after a scan; abort reconciliation on change. Treat non-`NotFound` subtree errors as an incomplete proof and retry, with a policy decision for permission loss. Scope trust per root/subtree rather than one boolean for all roots. This is moderate work and requires mount-namespace tests.

### 8. [BUG — high] Path identity broke hard-link accounting and alias freshness

**One sentence:** every hard-link name is now correctly a search row, but usage still sums rows as objects and watcher metadata updates only the alias named in the event.

**Evidence.** `usage.rs:25-32` explicitly says no hard-link work is needed because inode identity produces one row. That premise was removed. `entry_of` now always hashes the path; the rollup sums every live file row (`crates/scour-index-native/src/usage.rs:128-141`). The core type, CLI, MCP, and `AGENTS.md` still promise `du` semantics and one count per hard-linked object.

The scratch reproduction created a 4 KiB file and a hard link:

```text
nlink=2 logical_file=4096 indexed_files=2 indexed_bytes=8192 indexed_disk=8192
```

This directly regresses the wire contract. Search should return both names; reverting row identity to inode would reintroduce the just-fixed replacement bug. A second consequence is metadata drift: modifying through name A generates an event for A. A is re-statted and upserted, while name B's row retains its old size/timestamps until a full scan. Bind mounts and overlapping roots create the same object/name split at a larger scale.

The path change also invalidates historical measurements and design comments that still depend on `Caps::STABLE_IDS` (`docs/ENUMERATION.md:172,229`, portions of `docs/MEASUREMENTS.md`, and core `Key` documentation). In particular, an MFT/USN implementation must emit every real hard-link name while retaining object-to-alias information for metadata updates and usage; “one MFT record, one row” is no longer correct.

**Certainty:** disk usage is certain and reproduced. Alias freshness is high-confidence from event and identity semantics.

**Action and cost.** Keep two identities: row/name identity `(source, native path)` and optional object identity `(volume/subvolume, inode-or-file-id)`. Store/deduplicate the latter for usage, ideally only where link count is greater than one, and maintain an object-to-row alias map for metadata fan-out. Define bind-mount and cross-source accounting explicitly. This is a medium on-disk metadata addition; a usage-only dedup pass is a smaller interim fix but needs object identity captured by scan.

### 9. [BUG — high, security boundary] `stat` escapes a source through `..` and intermediate symlinks

**One sentence:** the textual source-owner check is not a filesystem containment check, so read-only clients can stat arbitrary machine paths and the web frontend can pass them to `xdg-open`.

**Evidence.** `Engine::stat` verifies only that the input string starts with a configured root at a component boundary (`crates/scour-engine/src/engine.rs:371-390,768-779`). `FsSource::stat` then calls `symlink_metadata` on that input (`crates/scour-source-fs/src/scan.rs:333-342`). `symlink_metadata` does not follow the final symlink, but the kernel resolves `..` and follows intermediate symlinks.

Both of these returned `/etc/passwd` metadata in the scratch reproduction:

```text
root/../../etc/passwd
root/outside/passwd       # outside -> /etc
```

The MCP exposes `scour_stat`. More seriously, `scour-web` documents `stat` as its “index fence,” then passes the returned `entry.path` to `xdg-open` (`apps/scour-web/src/main.rs:547-607`). Its token/origin defenses are good, but the claimed scope check is false.

**Certainty:** certain and reproduced.

**Action and cost.** Reject lexical `.` and `..`, but do not stop there. On Linux resolve a root-relative path through a root directory descriptor with `openat2(RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS)` and choose deliberately whether final symlinks may be inspected. Use capability-style platform equivalents elsewhere. `canonicalize` followed by a prefix check is still TOCTOU. Also decide whether stat means “this exact indexed native key” or “any current object beneath a source”; the web action requires the former. Moderate platform-specific work, plus security regression tests.

### 10. [RISK/BUG — high] Partial watch coverage is stale, silent, and overstated by status

**One sentence:** Scour can say a source is watched while newly failed subtrees are uncovered, and it loses the path/reason needed to repair them.

**Evidence.** Initial `cover` failures are recorded in `FsWatch.skipped`, but only printed once to stderr; `Status` reports only a count of source handles (`crates/scour-core/src/types/status.rs:13-40`). `start_watching` swallows per-source errors completely (`crates/scour-engine/src/engine.rs:233-253`). A source can therefore advertise `Caps::WATCH`, return `watching=1`, and have hundreds of holes with no protocol-visible flag.

Coverage added after a fresh-directory walk is worse. `WatchHandle::cover` puts failures in a local `Vec`, sends all resulting work to `Discard`, and throws the vector away (`crates/scour-source-fs/src/watch.rs:348-377`). The comment calls a watch-limit failure unactionable; it is exactly actionable, because it means future live updates below that path are not covered. `unwatched()` can never report this later failure.

The event re-stat path maps **every** error to `RemoveSubtree` (`watch.rs:230-267`). `ENOENT` warrants removal; `EMFILE`, `EACCES`, `ESTALE`, and transient I/O do not. Under load, a temporary inability to stat can hide a live tree and later persist that deletion.

**Certainty:** certain for discarded failures/error conflation; medium-to-high for frequency in production.

**Action and cost.** Make `cover` return a typed coverage result, update a shared set of uncovered prefixes, and schedule reconciliation/retry for readable failures. Only `NotFound` should remove; transient errors should record health and rescan/retry. Add status fields for uncovered subtrees/count, last watcher error code/time, overflow count, and last successful full reconciliation. A couple of days plus trait/status changes.

### 11. [BUG — medium/high] The advertised multi-component exclusions do not exclude their trees

**One sentence:** default `.git/objects` and `.cargo/registry` rules are ineffective for scans and mostly ineffective for watcher events, so high-churn caches enter the index despite being explicitly excluded.

**Evidence.** Platform defaults contain `.git/objects` and `.cargo/registry` (`crates/scour-source-fs/src/rules.rs:191-204`). Scan-side `Rules::excludes` compares only the entry basename to the full rule (`rules.rs:55-65`), which can never match a string containing `/`. Watch-side `excludes_path` checks an exact suffix while iterating components, but not descendants below that suffix (`rules.rs:79-103`).

The scratch tree included `.git/objects/aa/object` and `.cargo/registry/pkg/crate`; every directory and file survived the scan. No test covers a multi-component directory rule, even though the comments specifically claim it works.

**Certainty:** certain and reproduced.

**Action and cost.** Compile directory rules into component sequences once and apply the same matcher to scan and watch. Match the sequence at a component boundary anywhere in the path, then prune all descendants, subject to allow overrides. Add paired scan/watch tests for exact directory, descendants, misleading suffixes, case behavior, and allow. Small fix.

### 12. [RISK/BUG — medium] Exclusions can re-enable the index indexing itself

**One sentence:** a broad `exclude.allow` can override the hard-coded index-directory exclusion and revive the measured self-indexing feedback loop.

**Evidence.** Wiring appends the configured index directories to `exclude_paths` (`apps/scourd/src/wire.rs:91-116`) and calls the result “the index never indexes itself.” `Rules::excludes` tests `allow` first and returns false before examining excluded paths (`crates/scour-source-fs/src/rules.rs:55-60`). An allow beneath or equal to the index path therefore wins. The existing wiring test does not configure such an allow.

The comment records the cost when self-indexing previously happened: watcher and worker fed each other, consuming 36% and 26% of cores. This is not a hypothetical harmless entry.

**Certainty:** certain from rule ordering.

**Action and cost.** Separate non-overridable safety exclusions (index, socket/runtime state) from user exclusions, or reject an index directory beneath a source unless it is fenced before user rules. Add the one regression test. Hours.

### 13. [RISK — high on heterogeneous trees] Filesystem traits and scheduling are sampled once from roots, then applied across mounts

**One sentence:** nested or late-mounted filesystems inherit the root's case/mode/medium assumptions and thread count even though the walk deliberately crosses mount boundaries.

**Evidence.** `FsSource::new` probes `FsTraits` and `Medium` once per configured root and caches the reduction forever (`crates/scour-source-fs/src/scan.rs:24-64`). The walker sets `same_file_system(false)` (`scan.rs:174-199`). `fs.rs:171-177` explicitly admits nested mounts are judged by the root.

Consequences:

- constructing the source while `/mnt/depo` is an empty btrfs mountpoint and scanning it after NTFS appears retains btrfs `real_modes` and medium;
- an NTFS/FAT/FUSE/network mount nested under home is scanned with NVMe parallelism and the home filesystem's mode/case promise;
- a bind-mounted `/proc` at a non-default path is traversed because only absolute `/proc` is excluded;
- one cached `Caps::CASE_SENSITIVE` cannot describe mixed or Windows per-directory case behavior.

The “take the narrower promise across roots” policy does not see nested mounts and cannot update after a retry.

**Certainty:** high. A private mount-namespace test can demonstrate the exact metadata misclassification without touching real mounts.

**Action and cost.** Refresh root identity/traits at scan start and classify by device/mount during traversal. Give each device its own concurrency pool and policy. Default to not crossing mount boundaries unless configured, or discover mounts as explicit stable sub-sources. This dovetails with the unmount fix and is moderate work.

### 14. [BUG — medium] “Created” time is Unix ctime, and all timestamps lose sub-second precision

**One sentence:** on Linux the `dc:` query and `stat` output call inode status-change time “created,” so chmod/rename/metadata changes rewrite the supposed creation date.

**Evidence.** `Meta::from_std` stores `MetadataExt::ctime()` (`crates/scour-core/src/types/entry.rs:91-145`). The same file admits that ctime and Windows creation time are not the same (`entry.rs:98-100`). CLI rendering nevertheless labels it `created` (`apps/scour/src/render.rs:160-162`), and the query vocabulary exposes `dc` as creation. All three timestamps store epoch seconds, discarding nanoseconds available from Unix `statx` and Windows APIs.

**Certainty:** certain. `touch`, `chmod`, and a `scour stat --json` comparison is enough to demonstrate it.

**Action and cost.** Either rename the cross-platform field to status-changed where that is what it contains, or add a distinct birth-time field and use `statx(STATX_BTIME)` when supported. Preserve nanoseconds (or a clearly documented coarser unit) if ordering rapid changes matters. This is a wire/index format change; several days plus UI/i18n work.

### 15. [BUG — medium, terminal/model integrity] Human renderers print control characters and newlines from filenames verbatim

**One sentence:** a legal filename can forge extra output rows, corrupt columns, emit terminal control sequences, or restructure an MCP answer.

**Evidence.** CLI search/usage/stat directly interpolate `h.path`, `d.path`, and `e.path` in `println!` (`apps/scour/src/render.rs:37-50,107-145`). MCP does the same into newline-delimited prose (`apps/scour-mcp/src/render.rs:18-31,75-110`). Unix filenames may contain newline, tab, ESC, OSC sequences, and all bytes except NUL and `/`. JSON mode is safely escaped; the web page uses an HTML escape function.

**Certainty:** certain from renderer code. This is distinct from invalid UTF-8: a filename containing an actual newline is valid UTF-8 and survives scanning.

**Action and cost.** Escape controls in every human renderer using a stable, reversible display notation; leave the protocol/JSON native representation untouched. Treat terminal escape characters especially. Add newline, tab, ESC, and bidi-control fixtures. Small.

### 16. [BUG/GAP — high for stated targets] Windows does not compile; Android and full macOS are not validated

**One sentence:** the intended target claim is ahead of the build: the Windows workspace has three compile errors, and mobile/full-GUI targets have obvious unexercised platform holes.

**Evidence.** This command fails:

```bash
cargo check --offline --target x86_64-pc-windows-msvc --workspace
```

with:

```text
apps/scour-web/src/http.rs:93  cannot find `unix` in `os`
apps/scour-web/src/http.rs:105 no method `Permissions::mode`
crates/scour-source-fs/src/fs.rs:380 missing field `real_modes` in `FsTraits`
```

The non-GUI daemon/CLI/MCP/web/source/index subset cross-checks successfully for `x86_64-apple-darwin` and `x86_64-linux-android`; the Android source emits an unused-mut warning because it has no platform exclusions. Full workspace checks could not run offline because `accesskit_macos` and `android-activity` were not cached. Independently, `apps/scour-gui/src/main.rs:695-702` defines `cmd` only for Linux, macOS, and Windows, then uses it unconditionally; Android compilation will fail after dependencies are available. The web bridge assumes `xdg-open`, and Android falls into unknown filesystem traits/default exclusions.

Windows named pipes are named by username but explicitly lack an ACL (`crates/scour-config/src/paths.rs:41-62`). Another user who guesses the name can read indexed filenames and issue `rescan`, `maintain`, or `shutdown`. **Action and cost.** Put at least `cargo check` for Windows, macOS, and Android in CI; make platform-specific launch/runnable code conditional and define unsupported behavior. Add real VMs for watch, case, path, ACL, and filesystem semantics. Secure named pipes with the current user's SID ACL and set/check Unix socket permissions. The compile fixes are small; honest target support is a multi-cycle project.

### 17. [RISK — medium] Case semantics are advertised but unused

**One sentence:** `Caps::CASE_SENSITIVE` says it affects deduplication, but path identity, lookup, removal, and sweep always compare exact strings.

**Evidence.** `FsSource::caps` sets the flag from cached filesystem traits (`crates/scour-source-fs/src/scan.rs:115-132`); there is no index consumer of that capability. `EntryId` hashes exact UTF-8 spelling, and the ID tests explicitly treat `/a/b` and `/a/B` as distinct whatever the filesystem thinks. A case-only rename may work if the backend supplies a paired remove+create with canonical spellings, but a path event with a different case can leave two rows on a case-insensitive volume.

Windows makes volume-wide probing insufficient because NTFS also supports per-directory case sensitivity. macOS hardcodes APFS/HFS as insensitive even when formatted case-sensitive (`crates/scour-source-fs/src/fs.rs:435-453`), currently without effect because the flag is unused.

**Certainty:** certain that the capability is dead; medium that a specific backend emits casing sufficient to duplicate rows.

**Action and cost.** Define a source-provided native path equality/key operation, separate from search case folding and display spelling. Test case-only rename and alternate-spelling events on real case-insensitive Windows/APFS volumes. Do not implement this by globally Unicode-lowercasing paths; filesystem case rules are not Unicode default lowercase.

### 18. [RISK/GAP — medium] Long paths and deep trees depend on full-path syscalls

**One sentence:** the scanner reconstructs full `PathBuf`s and opens by full path, so Unix trees whose total path exceeds `PATH_MAX` can be present on disk yet unreadable to Scour.

**Evidence.** Such trees are constructible and traversable with directory-relative `openat` calls even when one absolute pathname exceeds 4096 bytes. The `ignore` walker and `de.metadata()` operate on accumulated paths; there is no dirfd-relative source API or test. Windows extended paths and native UTF-16 prefixes are normalized through string replacement without round-trip coverage beyond an ordinary `C:\Users` case.

**Certainty:** medium until a dirfd-created >4 KiB fixture is run against this exact `ignore` version.

**Action and cost.** Add the fixture first. A direct dirfd/getdents/statx scanner naturally fixes this as well as native-byte identity and mount tracking. If retaining `ignore`, document and surface the unreadable subtree instead of sweeping it. Moderate if folded into the scanner work.

### 19. [RISK/GAP — lower, but contract-relevant] Architecture and documentation have drifted after the identity change

**One sentence:** several load-bearing comments and measurements still describe inode identity, stable IDs, hard-link folding, or literal layer rules that current code violates.

**Evidence.** `Key` and `EntryId` documentation refers to the removed `Caps::STABLE_IDS` (`crates/scour-core/src/types/entry.rs:16-41`); `docs/ENUMERATION.md` still recommends it at lines 172 and 229; `usage.rs` and the wire contract still assert inode-folded hard links. The literal working agreement says `scour-engine` must never contain `notify`, `ignore`, or an implementation name, while its source/test comments do and its dev-dependencies/tests instantiate `NativeIndex`. Production dependencies are correctly abstract—this is contract/test placement drift, not runtime coupling.

**Certainty:** certain.

**Action and cost.** Update the contract and current-design portions of docs in the same identity-fix commit, while retaining clearly labeled historical measurement narratives where useful. Move concrete engine integration tests to a wiring/integration package or relax the literal test-only rule explicitly. Small, but it prevents future decisions resting on dead premises.

### 20. [BUG/GAP — medium] Several configuration knobs are promises with no implementation

**One sentence:** users can select faster scanning, a writer memory limit, path indexing, or scheduled maintenance and observe no behavioral change.

**Evidence.** `scan.fast` defaults true and is documented as the difference between a minute and ten, but `Config::scan_options` sets `skip_metadata: false` and wiring forces it false again (`crates/scour-config/src/schema.rs:294-306`, `apps/scourd/src/wire.rs:91-95`). `index.heap_mb` claims “the peak while indexing follows it,” but the index uses the fixed `MAX_STAGED = 100_000` and never reads the setting. `index.paths` and `service.maintain_every_hours` likewise have no consumers outside schema/tests/docs. The roadmap acknowledges this, but the shipped config still presents them as active.

**Certainty:** certain from whole-repository reference search.

**Action and cost.** Reject or hide inert keys until implemented; a parsed no-op is worse than an unsupported error. Wire `heap_mb` only after both staged builds and whole-index folds obey it. A real fast mode needs a second metadata pass, explicit partial-metadata status, and query semantics while it is incomplete. Removing misleading keys is small; implementing them honestly is medium/large.

## Performance and resource opportunities

### 21. [OPPORTUNITY] The warm critical path is the index builder, not enumeration

**One sentence:** on the measured warm local/NTFS workloads, eliminating every enumeration syscall cannot save as much as reducing path-to-segment construction.

**Evidence from this review.** I ran the existing raw and Rust walker binaries against the read-only `/mnt/depo` NTFS corpus, interleaving variants. All saw 1,565,767/1,565,768 entries with 20 threads:

| path | measured time |
|---|---:|
| raw `getdents64 + statx(BASIC|BTIME)`, first cache-warming run | 2,096.1 ms |
| raw `getdents64 + statx`, subsequent interleaved runs | 324.9–362.6 ms |
| `ignore` parallel walk + `metadata()` | 359.4–369.2 ms |
| Scour walker shape: metadata + `String` + lowercase + bounded channel | 632.3–703.1 ms |

Then I used the actual `FsSource` and `NativeIndex`, with Scour platform exclusions, path identity, 4,096-row engine-style apply batches, generation, sweep, and commit, into a new scratch index. It indexed 1,387,173 entries (2,956 excluded, zero unreadable):

| pass | total | accumulated `Index::apply` inside it | final sweep+commit |
|---|---:|---:|---:|
| fresh index, three observed runs | 2.376–2.482 s | 2.029–2.119 s | 156–200 ms |
| same paths reindexed | 2.971–2.974 s | 2.556–2.630 s | 183–245 ms |

The scan and apply timers overlap conceptually because the sink runs while the walker is active; accumulated apply time is nevertheless where the consumer thread was blocked. The result reproduces the repository's 2.27–3.07 s end-to-end range and does **not** reproduce the stated 6.3 s warm time.

Current `writepath 400000` runs (431,422 total mock entries including directories) were:

```text
bulk 757–885 ms (1.75–2.05 µs/entry)
rescan 944–1,021 ms (2.19–2.37 µs/entry)
8 re-upserts/commit: 0.2 ms mean, 0.3 ms worst
```

The repository profile identifies, per nominal 100k segment, trigram extraction (~36 ms), directory interning (~19 ms), sorting (~18 ms), and columns (~13 ms) as the largest builder pieces (`docs/MEASUREMENTS.md:1285-1326`). `DirWriter` copies each unique parent path into both `Vec<String>` and `HashMap<String, u32>` (`crates/scour-index-native/src/dirs.rs:109-132`). `TrigramWriter` allocates a 2 MiB seen bitmap plus a `HashMap<u32, List>` and postings vectors per build (`trigram.rs:108-175`). These are concrete optimization targets.

**Judgment.** A direct scanner can plausibly recover the 270–370 ms between the warm metadata walk and the full Scour walker shape, plus improve path correctness. On a 2.4 s warm build that is roughly a low-teens-percent ceiling, not a transformation. The builder and reindex path have the larger warm budget.

**What I would build.** First make commit publication transactional, then re-evaluate parallel segment construction. The previous correct attempt won 7/8 interleaved rounds but only by 11%, with ±10% noise; its first blocker—cross-builder hard-link dedup—changed with path identity, while its manifest blocker remains. Build independent segment bytes on a bounded worker pool, publish them only when all kills/new segments are transactionally ready, and retain deterministic correctness tests. Within each builder, remove duplicate directory strings, use arenas/borrowed keys, and profile trigram allocation with real filename distributions. Cost: moderate. Require an ABAB result on the same corpus before shipping.

### 22. [OPPORTUNITY] A direct Linux scanner is justified by correctness/integration, not by `statx` folklore

**One sentence:** `getdents64`/dirfd code becomes compelling when it simultaneously preserves bytes, supports >`PATH_MAX`, tracks mounts, and installs watches before enumeration; syscall reduction alone is a modest warm win.

The strong Linux design is one root-relative traversal:

1. open the root and record mount identity;
2. for each directory, install its inotify watch **before** reading children;
3. use `getdents64` into a 32 KiB buffer;
4. use `statx(dirfd, name, AT_SYMLINK_NOFOLLOW, needed metadata)` where metadata is required;
5. pass native name bytes/path-arena offsets to bounded segment builders;
6. queue all watch events until baseline generation+sweep publication, then replay;
7. route new devices/mounts through explicit policy and per-medium pools.

That removes `notify`'s second recursive tree walk, closes the startup gap, eliminates lossy/full-path conversions, makes mount identity available, and controls per-entry allocation. It is approximately 800–1,500 lines of Linux-specific unsafe/FFI plus tests and should remain an implementation crate behind `Source`.

Do **not** justify it with a reduced `statx` mask or `io_uring`:

- the repository measured every `statx` mask at 752–1,026 ns/call with no stable difference;
- synchronous statx measured 666 ns/call versus 723 ns/call through `io_uring`, whose statx operation is forced async;
- there is no merged `IORING_OP_GETDENTS`;
- 16 KiB–1 MiB directory buffers were within noise; 4 KiB was only 15–20% worse.

Those negative measurements are useful and should stand. Ext4 inode-order traversal remains an experiment, not a recommendation: the recorded cold trials reverse sign and variance exceeds effect. Test on a disposable ext4 image with controlled cache state before allocating design complexity.

### 23. [OPPORTUNITY] Cold and non-Linux enumeration need different answers

**One sentence:** warm local scans are build-bound, but boot-cold metadata and Windows/macOS bulk APIs can still produce multi-second wins.

The first raw NTFS run in this review was 2.096 s and later runs were ~0.33 s, showing the cache-state sensitivity directly. The repository's controlled cold figure is 7.657 s for `getdents64+statx` versus 1.425 s for a single-threaded `$MFT` parse; 1.270 s of the latter was a sequential 2.06 GiB read. That is a real cold-path opportunity. Warm MFT at 454 ms does not beat the 348 ms raw walk, so select it based on cold/startup objectives, not a universal “MFT is faster” claim.

Priority by platform:

- **Windows:** implement `GetFileInformationByHandleEx(FileFullDirectoryInfo)` first. It returns name, allocation/logical size, and four timestamps per directory buffer without a per-file open and without Administrator. Do not request a file ID variant that forces MFT lookups. Add raw UTF-16 path identity and ACL-secured change handling at the same time.
- **macOS:** use `getattrlistbulk`/`fts` with `ATTR_CMN_OBJTYPE`; avoid UUID/extended-security attributes that force per-entry fallback. Persist/replay a real FSEvents cursor and device UUID rather than `SinceNow`.
- **NTFS MFT/USN:** emit every non-DOS hard-link name and keep object-to-alias mapping. On Linux/ntfs3 probe `$MFT` at runtime and fall back. On Windows raw MFT/USN requires a privileged service and should come after the unprivileged bulk directory API.
- **btrfs:** the transid tree-search journal is technically excellent but `CAP_SYS_ADMIN` and the repository's 31×-slower full search make it unsuitable for the normal unprivileged daemon. A separate privileged helper is a product/security decision, not a scan optimization.

Cost ranges from medium for Windows directory buffers to large for a correct MFT parser/journal and privilege boundary.

### 24. [OPPORTUNITY] Large removals need temporal coalescing and an overflow-safe recovery path

**One sentence:** native subtree matching fixed the quadratic disaster, but a million-leaf event stream still pays repeated million-row bitmap passes and can trigger the overflow bug.

Current `removal 1000000 2000` on this host measured:

| removed paths in one commit | commit |
|---:|---:|
| 1 | 15.85 ms |
| 16 | 19.67 ms |
| 256 | 30.07 ms |
| 1,024 | 47.05 ms |
| 4,096 | 83.12 ms |
| one prefix covering the subtree | 17.69 ms |

This is excellent versus the documented old 2.24 s/4,096-path implementation. It also shows why `rm -rf` of a million files remains costly: children arrive before their parent, cross commit boundaries, fill the channel, and cause repeated segment passes.

Keep immediate in-memory hiding for user correctness, but debounce/coalesce durable removals slightly longer so a later ancestor absorbs leaf prefixes. When overflow occurs, discard the untrustworthy event tail and reconcile from the nearest known root rather than processing millions of stale hints. Measure end-to-end quiescence and missed-row count, not only one commit. Cost: small-to-medium after overflow correctness is fixed.

### 25. [OPPORTUNITY/DISAGREEMENT] Visibility should not require an immutable durable segment

**One sentence:** the 1 s watched/15 s idle clocks are reasonable batching clocks, but they are an unnecessary visibility clock and become a durability hole when startup does not reconcile.

Removals are hidden immediately; upserts remain invisible in `inner.staged` until commit (`crates/scour-index-native/src/index.rs:136-145`). With a live `Await`, the engine commits on the 1 s floor; without one, a quiet file may wait 15 s. Under a burst, 64 pending changes also wait for the 1 s minimum. This is a sensible segment-fragmentation policy, and the measured 0.2 ms for tiny update commits means the current active-window experience is not terrible.

I would nevertheless make a bounded in-memory delta searchable immediately and batch its WAL/segment publication separately. The delta is normally tens of rows and is capped at 100k; searching it with the same predicate after immutable segments gives sub-second semantic freshness without one segment per keystroke. A small WAL makes the recent delta restartable.

**Argument against my recommendation:** every query path, facet, usage answer, relevance ordering, and pagination rule must merge the mutable delta exactly. That is a substantial new correctness surface, and a 1 s active-window bound may be the better simplicity trade until restart reconciliation is fixed. I would fix on-start/journal and error durability first, then measure whether users can actually perceive the remaining second. Cost: medium/large.

### 26. [OPPORTUNITY/GAP] The 5.7 GB report is not explained by the streaming scan

**One sentence:** current evidence rules out “2.4 million `Entry`s accumulated by the walker,” but does not yet distinguish cgroup cache/kernel accounting from a later whole-index fold or a true allocator peak.

**Evidence.** The scanner-to-sink channel is bounded at 8,192 (`crates/scour-source-fs/src/scan.rs:210-219`). Native staging is bounded at 100,000 and shrunk on take (`crates/scour-index-native/src/index.rs:60,299-309`). My actual fresh+repeat scan of 1.387 M NTFS rows peaked at **244,432 KiB `VmRSS`**; a fresh-only pass peaked at 157,704 KiB. That process used the real source and native index but did not install 178k watches or compact.

I also sampled the repository's `scale 2000000` benchmark. It deliberately retains the entire generated corpus, builds 2.149 M rows, and performs a full rebuild; peak `VmRSS` was **867,980 KiB**, indexing was 5.3 s, rebuild 6.9 s, and post-trim anonymous memory was 3 MiB. Even this deliberately memory-heavy shape is far below 5.7 GB.

There are real high-water mechanisms:

- `fold` builds the entire replacement segment in `SegmentBytes` while old mmaps remain (`crates/scour-index-native/src/index.rs:487-556`);
- `build_sorted` simultaneously owns names/folded names, columns, dirs, IDs, trigrams, alive, provisional/remap vectors, and maps (`crates/scour-index-native/src/build.rs:71-119`);
- directory strings are duplicated and trigram postings are many small allocations;
- `malloc_trim` runs after folds, not after ordinary commits (`index.rs:824-842`);
- an automatic compact after a large generation can fold almost all 100k segments except the largest.

But systemd's cgroup `MemoryCurrent`/`MemoryPeak` is not process RSS: it includes charged file cache and kernel memory, and filesystem enumeration can charge substantial inode/dentry/page cache. If “systemd reported it” means that field, calling 5.7 GB RSS is likely the first error.

**What settles it.** During one isolated scan, sample every 50–100 ms:

```text
/proc/$PID/status: VmRSS, RssAnon, RssFile, VmHWM, Threads
/proc/$PID/smaps_rollup: Anonymous, Private_*, Shared_*, Rss
/sys/fs/cgroup/.../memory.current and memory.stat: anon, file, slab, sock
engine phase: watch-install / enumerate / apply / sweep / commit / compact
index counters: staged rows, segment being built/folded, builder bytes
```

Run once with compaction disabled and once with it forced, ABBA/interleaved if comparing allocator/build variants. Use heaptrack/DHAT or a profiling allocator for allocation stacks; do not infer them from RSS. If the actual `VmHWM` is near 5.7 GB, make fold external/streaming and enforce a real heap budget. If only cgroup `file/slab` is huge, the product decision is cache pressure/`MemoryHigh`, not a Rust leak. Cost to instrument: one day; streaming fold: major.

### 27. [RISK/BUG — medium] Bounds are enforced in selected frontends, not at the service boundary

**One sentence:** a direct/local client can request pathological depth, offset, facet vectors, or connection counts that consume work/memory far beyond the bounded reply the public frontends normally ask for.

**Evidence.** Search clamps `limit` but not `offset` (`crates/scour-engine/src/engine.rs:319-336`). Native search computes `need = offset + limit` and may retain/materialize every matching row up to that need (`crates/scour-index-native/src/index.rs:1092-1153`, `search.rs:974-1013`). A maximum `u32` offset forces a deep full build on 64-bit and can overflow `usize` arithmetic on intended 32-bit Android targets. The code intentionally reports `rows_built` because a 200k offset already measured 225 ms; it never establishes a ceiling.

`Engine::tree` caps only the per-level limit, not depth (`engine.rs:393-399`); total output can grow exponentially and recursion follows actual depth. Usage does not clamp `top` at all. MCP applies sensible caps, but CLI/direct protocol requests do not. Facets accept an arbitrary `Vec<FacetBy>` from the wire. The IPC request line is correctly capped at 1 MiB, but responses and client `read_line` are not capped, and the server spawns one thread per connection with no quota (`crates/scour-ipc/src/server.rs:83-103`, `client.rs:64-78`).

The web bridge's stated 16 KiB header cap is also incomplete: the request line uses `.take(MAX_HEAD)`, but each subsequent header uses unbounded `read_line` before the accumulated-size check (`apps/scour-web/src/http.rs:34-69`). A local unauthenticated peer can send one giant header line and grow memory before token validation.

**Certainty:** certain from boundary code; exact memory cost depends on corpus and request.

**Action and cost.** Validate and cap offset/work, depth, total tree nodes, usage top, facet dimension count, response line size, connection/thread count, and Await concurrency inside `scourd`/engine, regardless of frontend. Use checked arithmetic. Fix HTTP reading with one total capped reader. Small-to-medium, with adversarial wire tests.

## Measurement quality: what the numbers do and do not prove

### [GAP] The 6.3 s observation is cache-state dependent, not one stable ceiling

This review reproduced ~2.4 s fresh and ~3.0 s repeat indexing on the same 1.387 M-entry NTFS selection, while the first raw metadata walk was 2.096 s and later ones ~0.33 s. `docs/MEASUREMENTS.md:2836-2849` calls a 6.089 s Scour metadata walk warm, while `docs/ENUMERATION.md:19-24` calls a 593 ms Scour-shaped walk and 2.272–3.067 s end-to-end warm on essentially the same volume. Those statements cannot all describe the same binary, filters, cache state, and boundary.

The answer to “syscall-, I/O-, or lock-bound?” is therefore conditional:

- warm enumeration is neither the main wall-clock cost nor lock-bound in the isolated build; builder CPU/allocation dominates;
- a truly cold NTFS metadata walk can be I/O-bound and the repository's 7.657 s raw-versus-1.425 s MFT result shows the scale;
- a live service with searches and watch installation adds lock/contention and a second traversal that the isolated benchmark excludes.

Record filesystem, mount, exact commit/binary, filters/entry count, warm/cold preparation, watcher state, old-index state, and per-phase critical-path spans for every headline scan number. “Drop caches” on the user's busy host is not acceptable; use a disposable volume or repeat after a defined reboot, and interleave variants once warm.

### [BUG/GAP] One published phase table double-counts the overlapped pipeline

At `docs/MEASUREMENTS.md:1291-1298`, 271 ms walk + 1,862 ms apply + 132 ms sweep/commit equals 2,265 ms, not the listed 2,133 ms total. The quoted 12/82/6 percentages use 2,265 as their denominator. Because walker and sink overlap, cumulative nested timers are not additive wall-clock stages. The qualitative conclusion survives independent end-to-end data, but the table should say “cumulative work” or use critical-path spans. Add a trace timeline rather than percentages that imply serial stages.

### [BUG/GAP] Two benchmark helpers currently mismeasure what they label

- `crates/scour-index-native/examples/innerloop.rs:196-197` converts candidate blocks to rows using 128, while the shipped `columns::BLOCK` is 32 (`columns.rs:43-53`). Its “candidate rows, needle only” timing visits the wrong ranges.
- `SegmentBytes::total()` omits `fnames` (`crates/scour-index-native/src/build.rs:32-41`). The `bench` example therefore understates built segment bytes. Production `bytes_on_disk` walks real files and is not affected.

Fix both before adding their output to `MEASUREMENTS.md`, and add assertions tying helpers to format constants/component sums.

### [GAP] Peak-memory benchmarks report the post-trim point, not the peak

`scale` prints `anon_mb()` only after rebuild and `malloc_trim`; in my 2.149 M-row run it printed 3 MiB while an external 20 ms sampler observed 867,980 KiB peak RSS. Both numbers are true and answer different questions. Print pre-build, peak sampled, pre-trim, post-trim, RssAnon/RssFile, and cgroup breakdown. Do not use a single “anon MB” column to explain a systemd peak.

### [GAP] Important measurement programs live only in `/tmp`

The raw scanner, MFT parser, statx-mask, io_uring, and Rust walker-shape sources exist under `/tmp/fsbulk`, not the Cargo workspace. The commands in docs are useful on this host but not reviewable/versioned/reproducible elsewhere. Promote the durable, safe benchmarks into `tools/` or a separate benchmark repository with commit IDs, corpus manifests, and output capture. Keep privileged/destructive cache preparation explicit.

## The consistency proof that is missing

The current tests are strong for deterministic query answers and local happy-path watcher behavior. They do not prove that the index converges to disk under the failures above. I would add one stateful oracle suite and several focused layers.

### [GAP] Model-based quiescent consistency test

Run Scour against a disposable tree while an independent oracle operates on native paths. Generate reproducibly seeded operations:

- create, rewrite-in-place, temp+rename replacement, file/tree rename, delete leaf/tree;
- hard links across directories, unlink one alias, modify through another;
- invalid UTF-8/WTF-16, replacement characters, newline/tab/ESC/bidi controls;
- symlinks and intermediate symlink escape attempts;
- chmod/chown/timestamp changes and rapid sub-second rewrites;
- directories created already populated, clone/unpack-shaped bursts;
- overlapping/disjoint sources and config add/remove/reorder;
- dirfd-created paths longer than `PATH_MAX`.

At controlled quiescent barriers, wait for watcher delivery, commit, and revision, then compare the exact multiset `(stable source UUID, native path bytes/code-units, type, selected metadata)` against a raw `getdents/statx` or platform-native reference. Compare usage against an inode/file-ID deduplicating reference and queries against `scour-mock::brute_force`. The assertion is eventual equality after quiescence, not an impossible instantaneous snapshot during churn.

### [GAP] Watch-loss and startup barrier tests

- Inject an empty-path `EventKind::Other + Flag::Rescan` and assert a global rescan.
- Use a fake watcher with an explicit coverage barrier; mutate after scan observation but before coverage and prove startup still converges.
- Make `cover` fail after a fresh directory and assert status plus retry/reconciliation.
- Stall the worker, overflow a deliberately tiny fake event queue, then compare after recovery.
- Exercise create/populate/rename/delete trees while a full scan is in progress; verify queued events win after sweep.

### [GAP] Mount and partial-I/O tests

In a private mount namespace with loop/tmpfs test filesystems:

- scan empty mounted root versus unmounted mountpoint;
- unmount/remount before scan, midway through enumeration, before sweep, and during watch;
- replace the mount with a different device/filesystem at the same path;
- include one failed and one healthy root in a multi-root source;
- inject `EACCES`, `ESTALE`, `EIO`, `EMFILE`, and vanish-between-readdir/stat per subtree;
- verify no destructive sweep occurs without a complete, stable proof.

Some of this needs a privileged CI job; it should be isolated from ordinary developer machines.

### [GAP] Crash/fault matrix for every durable boundary

Wrap filesystem operations or introduce test-only failpoints. Fail the Nth create/write/short-write/fsync/rename/dir-fsync/open for manifest, every segment part, and alive bitmap. Kill a child process after each boundary. On reopen, require one of two states: the complete old transaction or the complete new transaction—never empty/default, silently partial, or unreopenable. Then run a full source oracle to prove recovery. Include `ENOSPC`, not merely permission errors.

### [GAP] Source/config persistence tests

Persist an index, stop, mutate disk, and restart under default config. Add/remove/reorder/rename sources and roots. Assert stable source mapping, removal/purge policy, and automatic reconciliation. The current disjoint two-source index test does not cover any of these lifecycle operations.

### [GAP] Cross-platform semantic CI

Cross-compilation catches the present Windows errors but not watcher semantics. Add real Windows and macOS jobs with case-only renames, per-directory case behavior, hard links, native-invalid string forms, long paths, FSEvents/inotify overflow signals, ACLs, and restarts. Android needs a declared product shape first: daemon lifecycle, IPC, storage permissions/scoped storage, UI launch behavior, and watch availability are not desktop Linux with another target triple.

## Explicit design disagreements

### [DISAGREEMENT] Fail-open configuration is the wrong availability trade

`Config::load_or_default` treats malformed TOML and any read error as permission to run the default configuration (`crates/scour-config/src/schema.rs:226-252`); `scourd` logs one line and proceeds (`apps/scourd/src/main.rs:38-48`). On a search engine, defaults are not neutral: they can change roots to the whole home directory, change index location/socket, enable watching, and leave old source rows under new numeric IDs. A transient config read failure may also lead to an attempted default save.

I would fail closed on an unreadable/malformed active config or load a durably stored last-known-good parsed configuration with a prominent unhealthy status. Do not silently index a different namespace.

**Argument for the current choice:** a desktop search service disappearing because of one typo is hostile usability, and the log gives an actionable reason. That argument would win if defaults only changed presentation. It loses when they redefine the data/security boundary. Last-known-good preserves availability without guessing. Cost: small-to-medium, including atomic config save and fingerprinting.

### [DISAGREEMENT] Empty roots should not be a mount detector

Keeping stale results for an absent removable disk is a defensible UX choice; deleting them at boot would be worse. But “directory has zero entries” is neither necessary nor sufficient evidence that a mount is absent. Record mount identity and source policy. A local ordinary source becoming empty should become empty in search. A configured removable mount whose device is absent may retain stale rows with an explicit offline flag. This makes the user-visible state honest instead of silently choosing one interpretation.

### [DISAGREEMENT] Reject overlapping sources until they are fully qualified

Supporting overlap can be useful—different policies or one aggregate source plus a narrower removable source—but current traits cannot preserve it. I would reject overlap now rather than document “first source wins.” The counterargument is that duplicate rows may be exactly what a multi-source model wants. If so, every change, sweep, usage attribution, owner lookup, and frontend result needs the source qualifier; implicit path ownership still cannot be correct.

## What is genuinely good

Briefly, because it should not hide the findings:

- The path-identity decision fixes the real temp+rename replacement failure, and the 64-bit digest followed by exact source/directory/name confirmation is the correct collision shape for representable paths.
- Watch-before-walk for newly discovered subtrees plus synchronous scan/event-queue replay is a good convergence design. Startup simply needs to use it.
- Bounded scan and watcher channels prevent the obvious unbounded-`Entry` memory failure; IPC request framing is also genuinely capped.
- Immutable mmapped segments, atomic manifest replacement, file and directory fsync, writer locking, and orphan cleanup show unusual care. The remaining problem is transactional error/crash behavior, not absence of durability work.
- The brute-force query verifier, response round-trip test, count/work instrumentation, and measured removal optimization are exactly the right habits.
- The native removal rewrite is a real success: 4,096 paths now commit in 83 ms here rather than the historical 2.24 s, while a subtree prefix stays near the one-pass floor.

## Recommended order of work

1. **Stop silent drift:** honor empty-path/flagged overflow; make watch coverage/errors/status observable; distinguish transient stat errors.
2. **Make index errors transactional:** retain staged state, propagate/retry failures, fail closed on manifest/component corruption, add fault injection.
3. **Guarantee restart convergence:** scan on start without a valid journal, establish coverage before baseline, persist source/config/mount identity.
4. **Fix the namespace model together:** native path keys, source-qualified changes/sweeps, stable source UUIDs, object identity for hard links, secure stat resolution. These interact and should share one format/contract revision rather than several lossy migrations.
5. **Repair smaller correctness issues:** multi-component and hard index exclusions, creation-time semantics, control-character rendering, request/work caps.
6. **Establish cross-target CI and fix Windows compilation/security.** Do not call Android supported until its process/UI/storage/watch model is specified.
7. **Instrument actual memory/cold phases.** Determine whether 5.7 GB is cgroup file/slab, `VmHWM`, or fold allocation before changing allocators.
8. **Optimize the measured sink:** transactional bounded parallel builders, directory/trigram allocation, then ABAB verification.
9. **Build integrated native enumeration/watch per platform:** Linux dirfd/getdents/statx/inotify for correctness and a modest warm win; Windows/macOS bulk APIs and journals for larger platform/cold wins; MFT only where its cold benefit pays for its complexity.
